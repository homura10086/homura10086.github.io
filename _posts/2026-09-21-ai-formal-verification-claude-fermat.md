# 当 AI 开始写数学证明：Anthropic 如何用 Claude 验证费马最后定理

1637年，皮埃尔·德·费马在阅读丢番图的《算术》时，写下了一句旁注：

> "我确信已发现一种美妙的证明，但此处空白太小，写不下。"

三个多世纪后，1994年安德鲁·维尔斯（Andrew Wiles）终于完成了证明。但这并不意味着故事结束——因为数学家们开始意识到，人类写的证明可能隐藏着细微的错误。于是，形式化验证（Formal Verification）应运而生：用计算机帮我们检查每一个逻辑步骤。

而最近，Anthropic 团队尝试了一个令人震惊的实验：让 Claude 协助完成数学定理的形式化验证。这不仅仅是"AI写代码"的故事，更是关于 AI 如何改变数学、工程甚至我们对"正确性"的理解。

## 形式化验证：为什么我们需要计算机来检查证明？

传统的数学证明依赖人类审稿人。但人类会犯错。2012年，数学家Viola Vaughan-Leggett发现了一个存在了15年的证明错误。更著名的例子是，怀尔斯在1993年首次发布证明后，被发现有一个致命漏洞——他花了整整一年才修复。

形式化验证解决了这个问题。它要求将数学命题翻译成形式化语言（如 Lean、Coq、Isabelle），然后计算机逐步骤验证每个推论是否符合逻辑规则。如果计算机说"通过"，就真的没问题了。

为什么重要？因为在航空、医疗、密码学等领域，一个被忽视的边界条件可能意味着生死。

## Anthropic 的实验：Claude 写出了数学证明？

Anthropic 的实验核心思路很直接：给定一个数学定理，Claude 尝试生成形式化证明的步骤。在这个过程中，研究人员发现了有趣的现象：

1. **Claude 擅长"搭建骨架"**：它能迅速生成证明的大致结构，识别出可能用到的引理
2. **但在细节上容易出错**：形式化语言对语法和类型要求极其严格，Claude 有时会生成"看起来合理但实际违反类型规则"的代码
3. **人机协作是关键**：研究员指定方向，Claude 生成候选步骤，研究员验证和纠正——形成了一个反馈循环

这个实验之所以引人注目，不仅因为它的技术含量，更因为它揭示了 AI 辅助形式化验证的可能性和局限性。

## 代码示例：在 Lean 4 中验证一个简单定理

下面是一个可以在 Lean 4 中运行的简单示例。你可以在 [Lean 4 的在线环境](https://live.lean-lang.org/) 或本地安装后运行：

```lean4
-- 先导入基本库
import Mathlib
import Aesop

set_option maxHeartbeats 0

open BigOperators Real Nat Topology Rat

-- 定理：对于任意自然数n，n + 0 = n
-- 这个看起来 trivially 的定理，在形式化系统里必须被明确证明
theorem add_zero_example (n : ℕ) : n + 0 = n := by
  -- 使用内置的加法单位元引理
  rw [Nat.add_zero]

-- 更有趣的例子：证明两个偶数之和是偶数
-- 定义：n 是偶数当且仅当存在某个 k 使得 n = 2 * k
def IsEven (n : ℕ) := ∃ k, n = 2 * k

theorem sum_of_evens_is_even (a b : ℕ) (ha : IsEven a) (hb : IsEven b) : IsEven (a + b) := by
  -- 从前提中提取存在性证据
  rcases ha with ⟨ka, ra⟩
  rcases hb with ⟨kb, rb⟩
  -- 构造新的证据：k = ka + kb
  use ka + kb
  -- 代入并化简
  rw [ra, rb]
  -- 证明 2*ka + 2*kb = 2*(ka+kb)
  ring
  -- ring 战术可以自动处理多项式恒等式
```

运行上述代码，你会看到 Lean 的编译器接受这些证明。这就是形式化验证的基本过程。

在 Anthropic 的实验中，Claude 被要求生成类似于上述结构的证明代码。当面对费马最后定理这样复杂的命题时，AI 必须处理更多的引理链、类型类约束和高级抽象。但基本范式是一样的。

## Spotify 的案例：为什么 AI 成本优化同样重要

Anthropic 的实验让人兴奋，但实际应用中还有一个现实问题：**成本**。Spotify 工程团队分享了一个令人印象深刻的案例——他们将 Claude Code 的 token 使用量减少了 90%。

这背后的优化手段包括：

1. **上下文剪枝**：仅将相关的代码文件和日志片段发送给 AI，而非整个项目
2. **提示压缩**：将冗长的说明压缩为更高效的提示模板
3. **缓存复用**：把常见任务的响应缓存起来，避免重复生成
4. **分层调用**：先用小型模型过滤明显不相关的请求，再把复杂任务路由给 Claude

假设你有一个每天调用 Claude 1000 次的工作流，token 优化直接影响到成本结构。这就是为什么"理论上可行"和"实践中经济"之间的差距，往往决定了一个项目能否落地。

## 警惕：AI 处理事故可能让工程师与系统失去联系

故事还没结束。如果我们把形式化验证的成功扩大到系统运维，会发生什么？

许多团队开始让 AI 处理生产事故：读取日志、生成修复建议、自动执行恢复步骤。这当然能缩短 MTTR（平均恢复时间）。但有研究指出，长期依赖 AI 处理事故可能导致一个隐患：

> **工程师逐渐失去对系统运行机制的第一手理解。**

当每次半夜的 Page 都是由 AI 自动响应，工程师就不再深入阅读原始日志，不再理解系统的状态机：

- 你知道这个服务是因为数据库连接池耗尽而崩溃的吗？还是因为内存碎片？
- 你能手动重现那个竞态条件吗？
- 当 AI 的建议出错时，你有没有调试它的第一手上下文？

形式化验证给了我们一个启示：**验证过程本身比验证结果更有价值**。通过形式化证明，数学家们重新理解了定理背后的结构。同样，工程师通过手动排查事故获得的系统洞察，是无法被替代的。

正确的使用方式不是"AI 代替工程师"，而是"AI 辅助工程师更快地理解系统"。例如：

```python
# 反例：完全依赖 AI 处理事故
def handle_alert(alert):
    suggestion = claude.generate_fix(alert.logs)
    execute(suggestion)  # 危险！工程师失去上下文

# 推荐：AI 辅助，人类保持理解
def handle_alert(alert):
    context = extract_relevant_context(alert)
    explanation = claude.explain(context)  # 生成解释，而非直接修复
    engineer.review(explanation)  # 工程师审查并执行
```

## 结论：AI 不是终点，而是新工具链的起点

Anthropic 用 Claude 协助形式化验证的实验告诉我们：AI 开始渗透到数学这种最抽象的领域。Spotify 的 token 优化案例提醒我们：应用 AI 必须考虑成本结构。关于 AI 处理事故的风险，则警示我们：工具再强大，也不能取代人类对系统的理解。

形式化验证的未来很可能不是"AI 自动证明一切"，而是"AI 生成候选证明，人类验证器确保 correctness"。这与工程实践中的"AI 辅助编码"异曲同工。

当费马写下那句著名的旁注时，他可能想不到，三个世纪后，人类会建造出能检查证明的计算机。而今天，我们正站在另一个转折点上：让 AI 成为形式化验证的协作者——既不是完全依赖，也不是完全排斥，而是在人类理解和机器验证之间，找到新的工作流。

这就是技术演进的常态：新工具出现，我们先惊叹，然后学习如何正确使用它。
